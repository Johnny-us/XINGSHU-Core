# 项目级授权后的持续协作

本文描述 XINGSHU 中通用的项目级持续授权与智能端协作边界，不提供后台唤醒、任务调度或宿主控制接口。

Owner（所有者）至少一次明确授权顶层项目。项目授权生效后，项目内的智能端可以在既定目标、公私边界、治理规则和实际技术权限内，自行拆分、创建和推进子项目、task、Work Order、Review 与修订，不需要因为每一个内部子项目再次请求 Owner 授权。

这不把任务发起权交给 Robot、Mailbox（项目邮箱）、Doorbell（到件提醒）或 Watcher（文件监听器）。这些确定性组件只能执行被分配的当前工作，不拥有创建、选择、启动或扩大新任务的权限。文件出现、提醒到达或传递成功本身不产生新的任务授权。

在项目常设授权内，两智能端可依据当前计划持续执行、Review（复核）与修订。普通项目内部循环不要求 Owner 逐轮复制正文或重复确认。计划调整由智能端维护当前任务状态；Relay 不承担计划、业务判断或授权推导。

只有事项真正越出已授权项目边界时，才重新请求 Owner，例如：开始无关的新项目；根本改变既定目标或公私边界；接入此前未授权的新私人数据、账号或安全凭据；新增高权限、公开监听或明显扩大系统访问权限；产生新的真实金钱、法律或身份代表义务；或者 Owner 已明确暂停、撤销授权，或出现既有项目原则无法裁决的互斥目标。

Mailbox 是持久交接和证据载体。接收智能端在项目授权范围内自行读取必要正文、核对完整性并保存自己的实际读取记录；Relay 不代读业务正文，不伪造端点回执。

Doorbell 或 Auto-Wake（后台唤醒）属于可选便利增强，不是固定两端协作主线的前置条件。即使未来实现，它最多负责机械提醒或触发既定流程，仍不拥有项目或任务发起权。

项目常设授权不取消工程真实性和安全门禁。Public Sync、代码变更、版本推进、Pull Request、Merge、Tag 或 Release 仍应经过适用的隐私检查、测试、独立 Review、公私分类和真实状态声明；这些门禁是项目内部工程控制，不等同于逐子项目重新向 Owner 请求授权。

`candidate`、`test`、`accepted`、`checkpoint` 或 Pull Request 不得被虚假升级或误称为正式 Release、active Runtime 或 production-ready（生产就绪）。
